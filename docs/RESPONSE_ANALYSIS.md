# Response Analysis

This document is the manual pre-implementation analysis matrix for the 30 supplied fixtures.

It is not an oracle derived from fixture frequency. Every expected finding must be traceable to:

- `docs/source/candidate-spec.md`;
- `docs/RULE_CATALOGUE.md`; or
- an explicitly documented ambiguity/interpretation in `docs/ASSUMPTIONS.md`.

## State Vocabulary

Use the following values where applicable:

- `YES`
- `NO`
- `UNKNOWN`
- `MALFORMED`
- `N/A`

For expected validation outcomes use stable rule IDs only.

## Confidence

Use:

- `HIGH` — directly supported by explicit specification language and fixture evidence.
- `MEDIUM` — supported, but dependent on a documented interpretation.
- `LOW` — materially affected by specification ambiguity; normally should not drive a FAIL without further evidence.

## Analysis Rules

1. Do not use `injectedBugs` as an oracle.
2. Do not infer correctness from what most fixtures contain.
3. Record malformed state explicitly rather than treating it as absent.
4. Separate contract, format/type, mathematical, and bounds defects.
5. Do not invent gameplay semantics.
6. If a calculation prerequisite fails, record the primary defect and mark dependent logic conceptually `NOT_EVALUABLE`.
7. Additional-component totals must only be checked where aggregation semantics are supported.
8. Record ambiguity separately from confirmed defect.
9. Likely-valid fixtures are important controls and must not be forced to contain findings.
10. The matrix is reviewed before implementation and again after the automated suite is complete.
